Unlike queries, mutations are typically used to create, update, or delete data on your canister, or perform side-effects. For this purpose, IC Reactor provides the `useActorMutation` hook.

## Basic Mutation

Here's an example of a mutation that creates a new post:

```tsx
import { useActorMutation } from "../reactor/hooks"

function CreatePost() {
  const { mutate, isPending, isSuccess, isError, error } = useActorMutation({
    functionName: "createPost",
  })

  return (
    <button
      onClick={() => {
        mutate([{ title: "My New Post", content: "Hello world!" }])
      }}
      disabled={isPending}
    >
      {isPending ? "Creating..." : "Create Post"}
    </button>
  )
}
```

A mutation can only be in one of the following states at any given moment:

- `isIdle` or `status === 'idle'` - The mutation is currently idle or in a fresh/reset state
- `isPending` or `status === 'pending'` - The mutation is currently running
- `isError` or `status === 'error'` - The mutation encountered an error
- `isSuccess` or `status === 'success'` - The mutation was successful and mutation data is available

Beyond those primary states, more information is available depending on the state of the mutation:

- `error` - If the mutation is in an `isError` state, the error is available via the `error` property.
- `data` - If the mutation is in an `isSuccess` state, the return data is available via the `data` property.

## Mutation Arguments

Arguments are passed to the `mutate` function as an array (matching the canister method signature):

```tsx
// Canister method: transfer(to: Principal, amount: nat64) -> Result<TransferReceipt, TransferError>
import { Principal } from "@icp-sdk/core/principal"

const { mutate } = useActorMutation({
  functionName: "transfer",
})

// Call with arguments as array, in raw Candid types
mutate([Principal.fromText("aaaaa-aa"), BigInt(1000000)])
```

<Aside type="note">
  Argument types follow the reactor the hooks were built from. A plain `Reactor`
  expects Candid values (`Principal`, `bigint`), while a `DisplayReactor`
  expects their display forms — the same call becomes `mutate(["aaaaa-aa",
  "1000000"])`.
</Aside>

## Side Effects

`useActorMutation` comes with helper options that allow quick and easy side-effects at any stage during the mutation lifecycle:

```tsx
const { mutate } = useActorMutation({
  functionName: "createPost",
  onMutate: (variables) => {
    // A mutation is about to happen!
    console.log("Creating post with:", variables)

    // Optionally return a context containing data to use when rolling back
    return { id: Date.now() }
  },
  onError: (error, variables, context) => {
    // An error happened!
    console.log("Rolling back with id:", context?.id)
  },
  onSuccess: (data, variables, context) => {
    // Boom baby!
    console.log("Post created:", data)
  },
  onSettled: (data, error, variables, context) => {
    // Error or success... doesn't matter!
    console.log("Mutation finished")
  },
})
```

When returning a promise in any of the callback functions, it will first be awaited before the next callback is called:

```tsx
const { mutate } = useActorMutation({
  functionName: "createPost",
  onSuccess: async () => {
    console.log("I'm first!")
  },
  onSettled: async () => {
    console.log("I'm second!")
  },
})
```

## Per-Mutate Callbacks

You can also provide additional callbacks to the `mutate` function itself. These are useful for component-specific side effects:

```tsx
const { mutate } = useActorMutation({
  functionName: "createPost",
  onSuccess: () => {
    // This fires first (from hook config)
  },
})

// In your component
mutate([{ title: "New Post", content: "Hello world!" }], {
  onSuccess: () => {
    // This fires second (from mutate call)
    navigate("/posts")
  },
})
```

<Aside type="caution">
  Per-mutate callbacks won't run if your component unmounts before the mutation
  finishes.
</Aside>

## Invalidating Queries After Mutation

The most common pattern after a mutation is to invalidate related queries. List
them in the `invalidateQueries` option:

```tsx
const { mutate } = useActorMutation({
  functionName: "createPost",
  invalidateQueries: [
    // Every getPosts query, whatever its args, infinite lists included
    { functionName: "getPosts" },
    // Only the getPost query for this id
    { functionName: "getPost", args: [postId] },
  ],
})
```

Each entry is one of:

- a method of the mutation's reactor, `{ functionName }` or
  `{ functionName, args }`. The method name and the args are type-checked
  against the canister, and the key is built when the mutation succeeds;
- a query object from `createQuery`, `createSuspenseQuery`,
  `createInfiniteQuery` or `createSuspenseInfiniteQuery`;
- a query factory from `createQueryFactory` and the other `create*Factory`
  functions, which covers every query it returns, whatever its args;
- a query key, from `generateQueryKey` or `getQueryKey()`.

With query objects and factories defined in a shared module, pass them as they
are:

```tsx
import { postsQuery, getPost } from "../queries"

const { mutate } = useActorMutation({
  functionName: "createPost",
  invalidateQueries: [postsQuery, getPost],
})
```

The invalidation runs after the canister call succeeds and before `onSuccess`.
The mutation stays pending until the invalidated queries that are in use have
refetched, so `onSuccess` reads the refetched data. `undefined` entries are
skipped, so `[maybeQuery]` is safe when a query is optional.

<Aside type="caution">
  Every query key starts with the canister ID, so a hand-written key such as
  `["getPosts"]` matches nothing. Name the method, pass the query object, or
  build the key with `generateQueryKey`.
</Aside>

For anything a fixed list cannot express, invalidate in `onSuccess`, and await
it so the mutation waits for the refetch:

```tsx
import { backend } from "../reactor"

const { mutate } = useActorMutation({
  functionName: "createPost",
  onSuccess: async (post) => {
    await backend.invalidateQueries({ functionName: "getPosts" })
    navigate(`/posts/${post.id}`)
  },
})
```

## Form Handling

Here's a complete example with form handling:

```tsx
import { useState } from "react"
import { useActorMutation } from "../reactor/hooks"

function CreatePost() {
  const [title, setTitle] = useState("")
  const [content, setContent] = useState("")

  const { mutate, isPending, isError, error, reset } = useActorMutation({
    functionName: "createPost",
    onSuccess: () => {
      // Clear form on success
      setTitle("")
      setContent("")
    },
  })

  const handleSubmit = (e: React.FormEvent) => {
    e.preventDefault()
    mutate([{ title, content }])
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={title}
        onChange={(e) => setTitle(e.target.value)}
        placeholder="Title"
        disabled={isPending}
      />
      <textarea
        value={content}
        onChange={(e) => setContent(e.target.value)}
        placeholder="Content"
        disabled={isPending}
      />

      {isError && (
        <div className="error">
          Error: {error.message}
          <button type="button" onClick={reset}>
            Dismiss
          </button>
        </div>
      )}

      <button type="submit" disabled={isPending}>
        {isPending ? "Creating..." : "Create Post"}
      </button>
    </form>
  )
}
```

## Async/Await with mutateAsync

If you prefer async/await syntax, use `mutateAsync`:

```tsx
const { mutateAsync, isPending } = useActorMutation({
  functionName: "transfer",
})

const handleTransfer = async () => {
  try {
    const result = await mutateAsync([recipient, amount])
    console.log("Transfer successful:", result)
    toast.success("Transfer complete!")
  } catch (error) {
    console.error("Transfer failed:", error)
    toast.error("Transfer failed")
  }
}
```

## Resetting Mutation State

Use the `reset` function to clear the mutation state:

```tsx
const { mutate, isError, error, reset } = useActorMutation({
  functionName: "createPost",
})

return (
  <div>
    {isError && (
      <div>
        <p>Error: {error.message}</p>
        <button onClick={reset}>Clear error</button>
      </div>
    )}
    <button onClick={() => mutate([{ title: "Test", content: "Test post" }])}>
      Create Post
    </button>
  </div>
)
```

## Optimistic Updates

Show the result before the canister answers with a query object's
`optimisticUpdate()`. Return it from `onMutate` and roll back in `onError`:

```tsx
import { createQueryFactory } from "@ic-reactor/react"
import { backend } from "../reactor"

// Module scope, next to the reactor
const getPost = createQueryFactory(backend, { functionName: "getPost" })

function LikeButton({ postId }: { postId: string }) {
  const { mutate } = useActorMutation({
    functionName: "likePost",
    // Cancels the post's fetch in flight, writes the new value, and resolves
    // with a rollback. `post` is typed from getPost; likes is a nat (bigint).
    onMutate: ([postId]) =>
      getPost([postId]).optimisticUpdate((post) => ({
        ...post,
        likes: post.likes + 1n,
      })),
    // The call failed: show the post as it was
    onError: (_error, _args, update) => update?.rollback(),
    // Refetch either way: a call that failed in transit may still have run
    onSettled: (_data, _error, [postId]) => getPost([postId]).invalidate(),
  })

  return <button onClick={() => mutate([postId])}>Like</button>
}
```

`optimisticUpdate` works on the query's raw data, before any `select`, and
calls the updater only when a value is cached: with nothing on screen there is
nothing to update. `rollback()` writes back the value from before the update
with its original fetch time, and invalidates it again if it was invalidated.
After a sign-in or sign-out it does nothing, since that value was the previous
principal's and the sign-in has already removed or refetched it.

Always refetch the query once the mutation settles: the fetch that
`optimisticUpdate` cancels may be a refetch an invalidation or a sign-in
started. `onSettled` above does that either way. To refetch only after a
success, list the query in `invalidateQueries: [getPost]` instead.

It works on the reactor's own QueryClient, so no `QueryClientProvider` is
needed. `useQueryClient()` throws without one; when you need the client itself,
use `backend.queryClient`.

## Mutation Factory

For reusable mutation configurations, use `createMutation`:

```tsx
import { createMutation } from "@ic-reactor/react"
import { backend } from "../reactor"

// Define mutation once
const createPostMutation = createMutation(backend, {
  functionName: "createPost",
  invalidateQueries: [{ functionName: "getPosts" }],
})

// Use in components
function CreatePost() {
  const { mutate, isPending } = createPostMutation.useMutation()
  // ...
}

// Or execute directly (outside React)
async function createPostInLoader(data: PostInput) {
  const result = await createPostMutation.execute([data])
  return result
}
```

`execute()` behaves like the hook path at the factory level: it runs the
factory's `onMutate`, then its `invalidateQueries` and `onSuccess` on success,
or its `onCanisterError` and `onError` on failure, then its `onSettled`, and
rethrows a failure so the `await` still rejects. See
[createMutation](/v3/reference/factories/createmutation) for details.

## Error Handling

IC Reactor provides structured error types for mutations:

```tsx
import { CanisterError, CallError } from "@ic-reactor/react"

const { mutate } = useActorMutation({
  functionName: "transfer",
  onError: (error) => {
    if (error instanceof CanisterError) {
      // Business logic error from canister (e.g., InsufficientFunds)
      if ("InsufficientFunds" in error.err) {
        toast.error(
          `Not enough funds. Balance: ${error.err.InsufficientFunds.balance}`
        )
      } else if ("InvalidRecipient" in error.err) {
        toast.error("Invalid recipient address")
      }
    } else if (error instanceof CallError) {
      // Network or agent error
      toast.error("Network error. Please try again.")
    }
  },
})
```

## Retries

Mutations retry nothing by default, as in TanStack Query, and that is the safe
default for update methods: each attempt is a new call under a new request
id, which the canister runs, so a retry after a lost response executes the
update twice. Set `retry` only for an update that is safe to repeat, or use
`reactorUpdateRetry`, which retries only a `SysTransient` rejection, the one
failure that proves the call never ran:

```tsx
import { reactorUpdateRetry } from "@ic-reactor/react"

const { mutate } = useActorMutation({
  functionName: "transfer",
  retry: reactorUpdateRetry,
})
```

A `mutations.retry` in the QueryClient's `defaultOptions` applies to every
mutation: `useActorMutation`, `useActorMethod`'s update calls, and
`createMutation` through both `useMutation()` and `execute()`. Prefer
`reactorUpdateRetry` there over a plain number.

## Type Safety

Like queries, mutations are fully type-safe:

```tsx
// Canister: createPost(input: PostInput) -> Result<Post, CreatePostError>

const { mutate } = useActorMutation({
  functionName: "createPost", // ✅ Autocomplete available
})

// ✅ TypeScript knows the argument type
mutate([{ title: "Hello", content: "World" }])

// ❌ TypeScript error: missing required field
mutate([{ title: "Hello" }])
```
