A client is built with exactly one way to say who calls (see
[The client](/v4/guides/client/)).

- `identity` is a caller that never changes: `"anonymous"` for a read-only
  client, or an `Identity` for a script, a server or a test. It has no sign-in.
- `auth` is a factory for a sign-in, and gives you users who sign in and out.
  This page is about `auth`.

Query keys carry the caller. When the user signs in or out, the client moves
every read to the new caller's keys, and nothing read for one principal shows
under another.

## Internet Identity with @icp-sdk/auth 10

The `AuthClient` of `@icp-sdk/auth` 10 is an `AuthLike` as it is. The
supported range is `^10.0.1`, and a weekly CI job checks the newest release
against `AuthLike`. A later release whose session has a state the client does
not know still compiles: the client calls anonymously in that state, and
`useAuth()` reads it as `"anonymous"`. npm's newest release is 11, which is
outside that range, so name the major version when you install it, and pass a
factory that builds one:

```sh
npm install @icp-sdk/auth@^10
```

```ts
import { createClient } from "@ic-reactor/core"
import { AuthClient } from "@icp-sdk/auth/client"

export const client = createClient({
  network: "ic",
  auth: (network) => new AuthClient(network),
})
```

You write no adapter. The client does the rest:

- It calls the factory once, on first use, and only in a browser. On a server
  the factory never runs and the client is anonymous.
- It owns what the factory returns. `client.dispose()` stops listening to it
  and calls its `dispose()`.
- It reads `getStatus()` and `getPrincipal()` to decide who calls, and asks
  `getIdentity()` for the identity to sign with.
- It sets a timer for the session's end, `getStatus().expiresAtMs`.
  `AuthClient`'s status turns `"expired"` by the clock and tells nobody, so
  the client tells its listeners itself: `useAuth()` renders `"expired"` when
  the session ends, with no user activity needed.
- It forwards `signIn(options)` and `signOut(options)` to it.
- If the factory throws, it is not called again. `new AuthClient()` reads
  `localStorage`, which throws where site data is blocked or in a sandboxed
  frame. The client then calls anonymously, so public reads still work, logs
  the error once in development, and rejects `signIn()` and `signOut()` with
  what the factory threw. Build a new client to try again.

`AuthClient` is not a peer dependency of core: you install `@icp-sdk/auth`
yourself when you want Internet Identity.

The factory returns the auth synchronously, so the module that builds the
client imports `AuthClient` statically, and, when the entry module imports
that module statically, a bundler puts it in the page's first chunk. To keep
the client, the sign-in code and the generated module out of that chunk
instead, lazy-load the component that holds the `ReactorProvider`: see
[Keep the IC stack out of the first load](/v4/guides/getting-started/#keep-the-ic-stack-out-of-the-first-load),
which also says what a route guard sees while it loads.

### The network the factory is handed

The client calls the factory with one argument, `network`, under
`AuthClient`'s own option names, so passing it through signs users in on the
network the client calls:

- `agentOptions` is the host, root key and `shouldFetchRootKey` of the
  client's own agents, and its `fetch`, when you gave one. `AuthClient` makes
  its mint and revoke calls with them.
- `identityProvider` is the Internet Identity to sign in with, as the two
  values `AuthClient` 10 takes (the page a person signs in on and the canister
  that mints their delegations), or absent, which `AuthClient` reads as
  mainnet's.

The client picks the identity provider by these rules, in order:

1. The `ic_env` cookie is trusted (see [The client](/v4/guides/client/)) and
   names `INTERNET_IDENTITY_PROVIDER`: that URL, with the cookie's
   `PUBLIC_CANISTER_ID:internet_identity`, or Internet Identity's own id,
   `rdmx6-jaaaa-aaaaa-aaadq-cai`, when it names none. The
   [Vite plugin](/v4/guides/vite-plugin/) writes this cookie in dev and
   preview.
2. The trusted cookie names an `internet_identity` canister but no URL: the
   project deploys its own Internet Identity, whose sign-in page cannot be
   derived from its id. No provider.
3. The network is `"local"`, or an object whose host is local: icp-cli's
   built-in Internet Identity, `http://id.ai.localhost:<port>/authorize` on
   the replica's port, with `rdmx6-jaaaa-aaaaa-aaadq-cai`. For `"local"` that
   is `http://id.ai.localhost:8000/authorize`, the Vite plugin's default too.
4. `"env"` on a local page whose cookie names no provider: the agent's host is
   the page's (a dev server, or a gateway serving an asset canister), which
   does not say where icp-cli's built-in Internet Identity is. No provider.
5. Any other network whose root key is not mainnet's (one given, from the
   cookie, or fetched): no provider.
6. Mainnet: no provider, and `AuthClient`'s defaults are right.

So in the [Vite wallet](/v4/examples/vite-wallet/), with `network: "env"` and
the plugin's cookie, the one line above signs in with the local Internet
Identity in dev and with mainnet's on a deployed page.

A local replica rejects every delegation mainnet's Internet Identity mints.
So in cases 2, 4 and 5, on a network that is not mainnet's, the client warns
when the factory reads `network.identityProvider`, as `new AuthClient(network)`
does. The warning comes once, in development: sign-in cannot work on this
network without an identity provider, and the line that names one is
`(network) => new AuthClient({ ...network, identityProvider: { authorizeUrl, canisterId } })`.
A factory that names its own provider, as that line does, or builds an auth
that is not Internet Identity, never sees the warning. Nor does a spread that
adds other options and names no provider, such as
`new AuthClient({ ...network, derivationOrigin })`: it does not read
`identityProvider`, so on these networks it must name one.

For the `internet_identity` your project deploys, `authorizeUrl` is the
sign-in page it serves and `canisterId` the id `icp deploy` gave its backend:

```ts
import { createClient } from "@ic-reactor/core"
import { AuthClient } from "@icp-sdk/auth/client"

// Your own Internet Identity: its sign-in page, and its backend canister.
const authorizeUrl = "http://my-ii.localhost:8000/authorize"
const canisterId = "bkyz2-fmaaa-aaaaa-qaaaq-cai"

export const client = createClient({
  network: "env",
  auth: (network) =>
    new AuthClient({
      ...network,
      identityProvider: { authorizeUrl, canisterId },
    }),
})
```

`identityProvider` takes both values or neither. A factory that takes no
argument, `() => new AuthClient()`, still works on mainnet. It ignores the
network the client hands it, so on any other network it signs in with
mainnet's Internet Identity, whose delegations the replica rejects, and the
client cannot tell that it did. On any network but mainnet, pass `network`
through.

**On dfx.** Rule 3 names icp-cli's built-in Internet Identity, which dfx does
not serve. A client of dfx's replica, `{ host: "http://127.0.0.1:4943" }`, is
handed `http://id.ai.localhost:4943/authorize`, a page that does not load,
and nothing warns. Name the Internet Identity your dfx project deploys, as
above: `authorizeUrl` is its sign-in page on dfx's gateway,
`http://<the id of the canister that serves it>.localhost:4943/authorize`,
and `canisterId` the canister that mints its delegations. It must be a release
of Internet Identity that answers the `ii_session_delegation` request
`@icp-sdk/auth` 10 signs in with.

### Sign-in options

`signIn` and `signOut` of the client and of `useAuth()` pass their argument to
the auth unchanged. For an `AuthClient` that is `maxTimeToLive` and
`maxTimeToIdle` (nanoseconds, as `bigint`) and `returnTo` for `signIn`, and
`returnTo` for `signOut`:

```tsx
import { useAuth } from "@ic-reactor/react"

const HOUR_NS = 3_600_000_000_000n

export function EightHourSession() {
  const { status, signIn, signOut } = useAuth()
  return status === "signed-in" ? (
    <button onClick={() => signOut({ returnTo: "/" }).catch(console.error)}>
      Sign out
    </button>
  ) : (
    <button
      onClick={() =>
        signIn({ maxTimeToLive: 8n * HOUR_NS, returnTo: "/account" }).catch(
          console.error
        )
      }
    >
      Sign in for 8 hours
    </button>
  )
}
```

The client types `options` as `unknown`, so a wrong option is not a type error.
Check it against `AuthClientSignInOptions` in `@icp-sdk/auth`.

`AuthClient` has more options, such as `openIdProvider: "google"` for a
one-click sign-in and `transport: "redirect"`. They belong to
`@icp-sdk/auth`, not to this library: the next section lists them.

### Internet Identity 2.0

What Internet Identity offers an app beyond a plain sign-in, its 2.0 features
among them, is an option of `AuthClient`, so it works through the factory, with
nothing from this library. An option of `new AuthClient()` goes in the factory,
beside `...network`, and is fixed for the client's life, since the client calls
its factory once. An option of `signIn()` goes in the call.

| To get                                            | Pass                                                                        | In                                          |
| ------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------- |
| One-click sign-in with Google, Apple or Microsoft | `openIdProvider: "google"`, `"apple"` or `"microsoft"`                      | the factory                                 |
| Sign-in with an organization's own SSO            | `ssoDomain: "example.com"`                                                  | the factory                                 |
| A verified email and the user's name              | `requestAttributes()` with `verified_email` and `name`                      | [Identity attributes](#identity-attributes) |
| A shorter session, or a shorter idle time         | `maxTimeToLive`, `maxTimeToIdle` (nanoseconds)                              | `signIn()`                                  |
| Sessions that only calls keep alive               | `disableBrowserActivity: true`                                              | the factory                                 |
| Two clients on one origin, each with its sign-in  | `namespace: "admin"` on one of them                                         | the factory                                 |
| One principal on several origins                  | `derivationOrigin`                                                          | the factory                                 |
| One sign-in for sibling subdomains                | `stateStorage: new CookieStateStorage({ domain })` and a `derivationOrigin` | the factory                                 |
| A full-page sign-in instead of a window           | `transport: "redirect"`                                                     | the factory                                 |

```ts
import { createClient } from "@ic-reactor/core"
import { AuthClient } from "@icp-sdk/auth/client"

// An admin console beside the main app on the same origin, signed in with
// the organization's SSO.
export const adminClient = createClient({
  network: "ic",
  auth: (network) =>
    new AuthClient({
      ...network,
      ssoDomain: "example.com",
      namespace: "admin",
    }),
})
```

- `openIdProvider` and `ssoDomain` exclude each other.
- `disableBrowserActivity` stops `AuthClient` from reading page visits, focus,
  pointer and keys as signs that the user is there. Calls are then the only
  sign, so a session in which the user only reads can reach its idle time.
- Sibling subdomains share one sign-in only when they share a principal, so
  every app passes the same `derivationOrigin`. A sibling whose browser holds
  the shared record but no credential of its own reads as
  `"signed-in-elsewhere"` (see [AuthState](#authstate)) and calls
  anonymously. Taking that sign-in over without asking the user again needs
  `prompt: "none"` and `hint`, which are options of the constructor, on a
  redirect route: see `@icp-sdk/auth`'s documentation.
- With `transport: "redirect"` the page itself goes to Internet Identity and
  comes back, so `AuthClient` asks for `signIn()` to be called on the page's
  load, not from a click, on a route of its own for each flow.

## Any other sign-in: AuthLike

An `AuthLike` is six methods and an optional `dispose`:

```ts nocheck
interface AuthLike {
  getPrincipal(): { toText(): string } | undefined
  getStatus(): {
    readonly state:
      | "signed-in"
      | "signed-in-elsewhere"
      | "expired"
      | "signed-out"
      // A state a later @icp-sdk/auth adds: the client calls anonymously.
      | (string & {})
    readonly expiresAtMs?: number // when the session ends, as Date.now() counts
  }
  getIdentity(): Promise<Identity>
  subscribe(listener: () => void): () => void
  signIn(options?: unknown): Promise<unknown>
  signOut(options?: unknown): Promise<unknown>
  dispose?(): void
}
```

The client reads `getStatus()` and `getPrincipal()` synchronously. It calls
`getIdentity()` only when it builds or checks an agent for a signed-in
principal, and it reads both again after every `subscribe()` notification.
Only the state `"signed-in"` makes the client call as `getPrincipal()`. Every
other state calls as the anonymous principal.

`expiresAtMs` is optional. When the status carries it while `"signed-in"` or
`"signed-in-elsewhere"`, the client sets a timer for it and reads the status
again then, so an `AuthLike` whose status turns `"expired"` by the clock need
not notify for it. A deadline that has passed while the status still says
`"signed-in"` sets no timer. And whenever `client.caller()` or
`client.authState()` reads a change no notification announced, the client
tells its listeners in a microtask.

`getIdentity()` should return the same object until the identity really
changes. The client builds a new agent for every new identity object it is
handed, and reads a new object for the same principal as a renewal.

Any other sign-in that hands over an `Identity` fits with a small adapter:
one that gives a delegation (a hand-rolled session, or Internet Identity
through a client other than `AuthClient`) or a key (a local dev account).
This is the one in the guide, `packages/core/llms.txt`:

```ts
import type { AuthLike } from "@ic-reactor/core"
import type { Identity } from "@icp-sdk/core/agent"

export interface SignInSource {
  getIdentity(): Identity // anonymous while signed out
  isAuthenticated(): boolean
  login(): Promise<void>
  logout(): Promise<void>
  subscribe(listener: () => void): () => void
}

export function toAuthLike(source: SignInSource): AuthLike {
  const signedIn = () =>
    source.isAuthenticated() &&
    !source.getIdentity().getPrincipal().isAnonymous()
  return {
    getPrincipal: () =>
      signedIn() ? source.getIdentity().getPrincipal() : undefined,
    getStatus: () => ({ state: signedIn() ? "signed-in" : "signed-out" }),
    getIdentity: async () => source.getIdentity(),
    subscribe: (listener) => source.subscribe(listener),
    signIn: () => source.login(),
    signOut: () => source.logout(),
  }
}
```

One client has one `auth`. To offer two sign-in sources, write one `AuthLike`
that holds both and picks one from the options of `signIn`. The Vite wallet's
`src/auth/wallet-auth.ts` does this for Internet Identity and a local dev
account.

### Wallets that sign each call

A wallet used through ICRC-25, ICRC-27 and ICRC-49 (OISY, Plug, an NFID
account) signs each call: the user approves it in the wallet, which signs and
sends it, and the app never holds an `Identity`. Used this way, the wallet is
not an `AuthLike`, and the client cannot send as it. (A wallet that also
speaks ICRC-34 can hand the app a delegation instead, from
`signer.requestDelegation()`; a `DelegationIdentity` made from it is an
`Identity`, and an `AuthLike` can hold it as for Internet Identity above.) Keep the client for reads, anonymous (a ledger's balances are
public; `SignerAgent` would send each read to the wallet for approval too),
and send the wallet's writes through `SignerAgent` from `@icp-sdk/signer`,
then invalidate the reads yourself:

```ts
// src/wallet.ts: needs @icp-sdk/signer, @icp-sdk/canisters and @dfinity/utils
import { createClient } from "@ic-reactor/core"
import { IcrcLedgerCanister } from "@icp-sdk/canisters/ledger/icrc"
import { Principal } from "@icp-sdk/core/principal"
import { Signer } from "@icp-sdk/signer"
import { SignerAgent } from "@icp-sdk/signer/agent"
import { PostMessageTransport } from "@icp-sdk/signer/web"
import { actor, type Actor } from "./generated/icrc1"

const LEDGER = "ryjl3-tyaaa-aaaaa-aaaba-cai"

// Reads: the client, anonymous.
export const client = createClient({ network: "ic", identity: "anonymous" })
export const ledger = client.canister<Actor>(actor, { id: LEDGER })

type Account = Awaited<ReturnType<Signer["getAccounts"]>>[number]

// The wallet's window may open only in a click handler: call connect()
// straight from a "Connect" button's onClick, before any await.
export async function connect(
  // A wallet may share several accounts (NFID does): let the user pick one.
  choose: (
    accounts: Account[]
  ) => Account | undefined | Promise<Account | undefined> = (accounts) =>
    accounts[0]
) {
  const signer = new Signer({
    transport: new PostMessageTransport({ url: "https://oisy.com/sign" }),
    // Keep the channel open between the requests of one session.
    autoCloseTransportChannel: false,
  })
  try {
    // ICRC-27: the accounts the user shares. A wallet that lacks it cannot
    // be used this way; signer.getSupportedStandards() says which it has.
    const account = await choose(await signer.getAccounts())
    if (!account) throw new Error("the wallet shared no account")
    const agent = await SignerAgent.create({ signer, account: account.owner })
    const wallet = IcrcLedgerCanister.create({
      agent,
      canisterId: Principal.fromText(LEDGER),
    })
    // The whole account: its subaccount, if any, is the one to debit. Call
    // disconnect() when the session ends, or before connecting again: it
    // closes the wallet's window, which stays open otherwise.
    return { account, wallet, disconnect: () => signer.closeChannel() }
  } catch (error) {
    // Cancelled or failed: close the window the request opened.
    await signer.closeChannel()
    throw error
  }
}

// Writes: through the wallet, which shows each call to the user.
export async function send(
  { account, wallet }: Awaited<ReturnType<typeof connect>>,
  to: Principal,
  amount: bigint,
  // Nanoseconds since the epoch, BigInt(Date.now()) * 1_000_000n, fixed
  // per transfer so a re-send is deduplicated.
  createdAt: bigint
) {
  try {
    return await wallet.transfer({
      // Without it the ledger debits the owner's default subaccount.
      from_subaccount: account.subaccount,
      to: { owner: to, subaccount: [] },
      amount,
      created_at_time: createdAt,
    })
  } finally {
    // The client did not send this write, so it cannot invalidate for it.
    await client.queryClient.invalidateQueries({
      queryKey: client.queryKey(ledger),
    })
  }
}
```

What the client gives a write does not reach this one: no `ReactorError`, no
`mayHaveExecuted`, no invalidation of its own. Read the failure yourself:

- A `SignerError` (from `@icp-sdk/signer`) with ICRC-25's code `3001`, action
  aborted, is the user's refusal: nothing was sent.
- A ledger `Err` (`IcrcTransferError` from `@icp-sdk/canisters`) means the
  ledger answered and did not move the funds.
- Anything else after the user approved, a closed wallet window included, can
  mean the transfer ran. Read the balance, or send the same transfer again
  with the same `created_at_time`, which the ledger answers `Duplicate` if
  the first went through.

Show the wallet's account (`account.owner`, and its subaccount when it has
one) as the user's, not `useAuth()`'s principal, which stays anonymous. A wallet that is a browser extension (Plug) connects with
`BrowserExtensionTransport` from `@icp-sdk/signer/extension` instead.
`@icp-sdk/signer` peers only `@icp-sdk/core` 6, so it installs beside the
client. NFID IdentityKit 2.0 does not: it peers `@icp-sdk/auth` 5, and npm
refuses it beside the `@icp-sdk/auth` 10 the client uses.

## AuthState

`client.authState()` and `useAuth()` give an `AuthState`: a `status`, a
`principal` and, while signed in, `expiresAt`.

| The auth says         | `status`                | `principal`          |
| --------------------- | ----------------------- | -------------------- |
| `signed-in`           | `"signed-in"`           | the signed-in user's |
| `signed-out`          | `"anonymous"`           | `2vxsx-fae`          |
| `expired`             | `"expired"`             | `2vxsx-fae`          |
| `signed-in-elsewhere` | `"signed-in-elsewhere"` | `2vxsx-fae`          |

`principal` is the principal calls go out as, so in every state but
`"signed-in"` it is the anonymous principal, and a check such as
`principal !== "2vxsx-fae"` means what it looks like. An expired session
and one signed in on a sibling origin cannot sign a call, so they do not name
their principal. To say whose session ended, read the auth's own
`getStatus()`, which keeps it. For that you need your own reference to the
`AuthClient` (see
[Your own reference to the AuthClient](#your-own-reference-to-the-authclient)),
because the client does not expose its auth.

`expiresAt` is when the session ends, in milliseconds since the epoch (as
`Date.now()` counts; `new Date(expiresAt)` for a date), so you can show
"signed in until". It is there only while `status` is `"signed-in"` through an
auth whose `getStatus()` carries `expiresAtMs`, as `AuthClient` 10's does.
When that time passes, the status turns `"expired"` and listeners are told.

A client built with `identity` reports `"signed-in"` with that identity's
principal, or `"anonymous"` for `"anonymous"` and for an explicit
`AnonymousIdentity`, with no `expiresAt`. A client on a server reports
`"anonymous"`.

<Aside type="caution" title="Signed in may be read-only">
  Since `@icp-sdk/auth` 10.0.0, `AuthClient` acts for sessions that Internet
  Identity scoped to queries only. Such a session reports `"signed-in"`, and the
  network refuses its updates. `@icp-sdk/auth` does not expose the scope yet, so
  `AuthState` cannot tell the two apart: `"signed-in"` means calls are signed by
  `principal`, not that a write will be accepted. Handle an update's rejection
  as you would any other.
</Aside>

## useAuth

`useAuth()` returns the `AuthState` plus `signIn` and `signOut`:

```tsx
import { useAuth } from "@ic-reactor/react"

export function SessionButton() {
  const { status, principal, signIn, signOut } = useAuth()
  if (status === "signed-in") {
    return (
      <button onClick={() => signOut().catch(console.error)}>
        Sign out {principal}
      </button>
    )
  }
  return (
    <>
      {status === "expired" && <p>Your session expired.</p>}
      <button onClick={() => signIn().catch(console.error)}>Sign in</button>
    </>
  )
}
```

- A component that calls it renders once for each change of `status`,
  `principal` or `expiresAt`, and never otherwise. A renewed delegation does
  not render it. A session that ends by the clock renders it with
  `"expired"` when it ends.
- The object it returns is the same until one of them changes, so it is safe
  in a dependency array or as a prop of a memoized child.
- It is `"anonymous"` on a server and during a hydrating render, even when the
  browser holds a session, so the HTML matches the server's. The component
  renders again with the real state right after hydration. Show the same thing
  signed out and while the session is read. See
  [SSR and hydration](/v4/guides/ssr/).
- It throws outside a `ReactorProvider`.

`signIn` and `signOut` return a promise, and the promise can reject:

- on a client built with `identity`, with a `TypeError`: there is no sign-in;
- on a server, and after `client.dispose()`, with an `Error`;
- with what the auth factory threw, when it threw;
- with whatever the auth rejects with, never a `ReactorError`. `AuthClient`
  rejects when the user closes Internet Identity's window or the browser
  blocks it, and rejects a sign-in that a later sign-in or sign-out took over
  from with a `SupersededError`, which you can usually ignore.

Always catch them, as the examples do.

```tsx
import { useAuth } from "@ic-reactor/react"
import { SupersededError } from "@icp-sdk/auth/client"
import { useState } from "react"

export function SignInButton() {
  const { signIn } = useAuth()
  const [failure, setFailure] = useState<string>()
  return (
    <>
      <button
        onClick={() =>
          signIn().catch((error: unknown) => {
            if (error instanceof SupersededError) return
            setFailure(error instanceof Error ? error.message : String(error))
          })
        }
      >
        Sign in
      </button>
      {failure !== undefined && <p role="alert">{failure}</p>}
    </>
  )
}
```

Outside React, `client.authState()` is the same state, and
`client.subscribe(listener)` calls `listener` once after each change of it.
It returns a function that stops listening.

```ts
import { client } from "./ledger"

const stop = client.subscribe(() => {
  const { status, principal } = client.authState()
  console.log(`caller is now ${principal} (${status})`)
})

// later
stop()
```

## When the caller changes

| Question               | Answer                                                                  |
| ---------------------- | ----------------------------------------------------------------------- |
| the caller's principal | `useAuth().principal`, `client.caller()` (`2vxsx-fae` unless signed in) |
| may a write be sent    | `useAuth().status === "signed-in"`; the client refuses the rest itself  |
| when did it change     | `useAuth()` re-renders; `client.subscribe(fn)`                          |

A `"signed-in"` session may still be read-only (see [AuthState](#authstate)).

A call goes out as the principal that was current when it was made, or not at
all. The client keeps one agent per principal and never points an agent at
another identity. What that means in practice:

- **Components.** `useClient()` re-renders its component on a sign-in, a switch
  of account and a sign-out, and returns a new object for the new caller, so
  the options it builds in that render use the new caller's keys, and a
  `useMemo` or effect that lists it in its dependencies (or React Compiler's
  cache) builds them again. A change of status that keeps the caller (a
  session that expired, one signed in elsewhere) renders nothing, because
  both already called anonymously. Call `useClient()` in the body of each
  component that builds options, on every render.
- **Reads in flight.** A read started for the old caller is cancelled when
  someone else is current, before anything is sent. It fails with
  `kind: "cancelled"` and `code: "caller_changed"`, and it never lands in the
  new caller's key. Treat this error as "ignore" (see
  [Errors](/v4/guides/errors/)).
- **Writes.** A write goes out as the caller current when `mutate()` was
  called, or not at all. When TanStack Query holds it back (offline, or
  queued behind another mutation of its `scope`) and the account changes in
  between, it fails with `kind: "cancelled"`, `code: "caller_changed"` and
  `mayHaveExecuted: false`, and nothing is sent. Built from a render's
  `useClient()`, its options also send only as that render's caller: a press
  handled before a switch reached the render is refused the same way. If
  nobody is signed in, the client refuses it before sending:
  `kind: "unauthenticated"`, code `anonymous_write`.
- **Data.** After a sign-in, a sign-out or a switch, the new keys are empty
  until they load. Do not use `placeholderData: keepPreviousData` or an
  `initialData` taken from another key: it would show one principal's data to
  another.

A read that waits for a user uses `skipToken` (see
[Reads](/v4/guides/reads/)):

```tsx
import { principal } from "@candid-core/schema"
import { useClient, useAuth } from "@ic-reactor/react"
import { skipToken, useQuery } from "@tanstack/react-query"
import { actor, type Actor } from "./generated/icrc1"

export function MyBalance() {
  const client = useClient()
  const { status, principal: caller } = useAuth()
  const ledger = client.canister<Actor>(actor, {
    id: "ryjl3-tyaaa-aaaaa-aaaba-cai",
  })
  const balance = useQuery(
    client.queryOptions(
      ledger,
      "icrc1_balance_of",
      status === "signed-in"
        ? { owner: principal(caller), subaccount: null }
        : skipToken
    )
  )
  if (status !== "signed-in") return <p>Sign in to see your balance.</p>
  return <p>{balance.data?.toString() ?? "…"}</p>
}
```

## Identity attributes

Internet Identity can sign attributes about the user for your canister, such
as their name and an email address. The canister reads them from a call that
carries them, and they reach it in three steps:

1. Your canister issues a nonce: an update call to
   `_internet_identity_sign_in_start`, made as the anonymous principal, which
   returns a `blob`.
2. The app signs in and asks for the attributes with that nonce. Started
   together, they are one Internet Identity interaction for the user. The
   answer is the attributes, Candid-encoded, as `data`, and Internet
   Identity's `signature` over them.
3. The app calls `_internet_identity_sign_in_finish` as the signed-in user,
   with `data` and `signature` attached to the call as its `sender_info`. The
   canister checks them and keeps what it needs.

DFINITY's `identity-attributes` library adds both methods to a canister and
makes the checks: [`mo:identity-attributes`](https://github.com/dfinity/identity-attributes/tree/main/motoko)
for Motoko, a mixin you `include`, and the
[`identity-attributes`](https://github.com/dfinity/identity-attributes/tree/main/rust)
crate for Rust, `#[identity_attributes]`. Both answer with the same Candid, so
the app's side below works with either. Their READMEs say how to set the
canister up. They pair the library with `@icp-sdk/auth` 7, whose
`requestAttributes` takes the nonce as a promise; in 10 it takes a function
that returns one, as below.

The app's client calls every update as the signed-in user and attaches
nothing to a call, so steps 1 and 3 each go through a second client on the
same network, built for that one call and disposed after it:

- Step 1 through a client built with `new AnonymousIdentity()` from
  `@icp-sdk/core/agent`, which may send an update as the anonymous principal.
  A client built with `identity: "anonymous"`, like a signed-out one, refuses
  an update before it sends it.
- Step 3 through a client built with an `AttributesIdentity` from
  `@icp-sdk/core/identity`, which attaches `data` and `signature` to each call
  it signs.

Step 2 needs the `AuthClient` itself, which the client does not hand out, so
you keep your own reference to it.

### Your own reference to the AuthClient

Keep what each client's factory builds, beside the client:

```ts
import { createClient, type Client } from "@ic-reactor/core"
import { AuthClient } from "@icp-sdk/auth/client"

/** The app's network, for its client and the clients built beside it. */
export const network = "ic"

/** Internet Identity's canister, where the factory is handed no provider. */
const INTERNET_IDENTITY = "rdmx6-jaaaa-aaaaa-aaadq-cai"

interface Built {
  readonly authClient: AuthClient
  /** The canister that mints the sign-in, which signs the attributes too. */
  readonly signer: string
}

const builtBy = new WeakMap<Client, () => Built | undefined>()

/** What `client`'s auth factory built, once it has run. */
export const getAuthClient = (client: Client) => builtBy.get(client)?.()

export function createAppClient(): Client {
  let built: Built | undefined
  const client = createClient({
    network,
    auth: (handed) => {
      const authClient = new AuthClient({ ...handed, openIdProvider: "google" })
      built = {
        authClient,
        signer: handed.identityProvider?.canisterId ?? INTERNET_IDENTITY,
      }
      return authClient
    },
  })
  builtBy.set(client, () => built)
  return client
}
```

Hand it to the provider, `<ReactorProvider client={createAppClient}>`, or, in
an app with no server render, call it once in a module. The client still owns
the `AuthClient` and disposes it with itself. The factory runs in a browser,
on first use, so `getAuthClient(client)` is `undefined` on a server and until
the client has built its auth.

### Sign in with attributes

```ts
import { createClient, type Canister, type Client } from "@ic-reactor/core"
import { scopedKeys } from "@icp-sdk/auth/client"
import { AnonymousIdentity, type Identity } from "@icp-sdk/core/agent"
import { AttributesIdentity } from "@icp-sdk/core/identity"
import { Principal } from "@icp-sdk/core/principal"
import { getAuthClient, network } from "./auth-client"
import { actor, type Actor as Accounts } from "./generated/accounts"

const ACCOUNTS_ID = "be2us-64aaa-aaaaa-qaabq-cai"

/** One call to the accounts canister as `identity`, through a client of its own. */
async function callAs<T>(
  identity: Identity,
  call: (accounts: Canister<Accounts>) => Promise<T>
): Promise<T> {
  const client = createClient({ network, identity })
  try {
    return await call(client.canister<Accounts>(actor, { id: ACCOUNTS_ID }))
  } finally {
    client.dispose()
  }
}

/**
 * Signs in, has the accounts canister verify the user's name and email, and
 * returns what Internet Identity signed.
 */
export async function signInWithAttributes(app: Client) {
  // Builds the auth if the client has not yet, and opens Internet Identity.
  const signedIn = app.signIn()
  const built = getAuthClient(app)
  if (built === undefined) {
    await signedIn // on a server it rejects, and says why
    throw new Error("This client was not built by createAppClient")
  }
  const { authClient, signer } = built

  // 1 and 2: the nonce, and the attributes in the same interaction.
  const [, attributes] = await Promise.all([
    signedIn,
    authClient.requestAttributes({
      keys: scopedKeys({
        openIdProvider: "google",
        keys: ["name", "verified_email"],
      }),
      nonce: () =>
        callAs(new AnonymousIdentity(), (accounts) =>
          accounts._internet_identity_sign_in_start()
        ),
    }),
  ])

  // 3: the finish call, with the attributes as its sender_info.
  const identity = new AttributesIdentity({
    inner: await authClient.getIdentity(),
    attributes,
    signer: { canisterId: Principal.fromText(signer) },
  })
  await callAs(identity, (accounts) =>
    accounts._internet_identity_sign_in_finish()
  )

  // The app's client did not send that write, so it cannot invalidate for it.
  await app.queryClient.invalidateQueries({
    queryKey: app.queryKey(app.canister<Accounts>(actor, { id: ACCOUNTS_ID })),
  })
  return attributes
}
```

This imports `./auth-client`, the module above, and `./generated/accounts`,
the module `candid-core-cli gen` writes for the accounts canister's `.did`.

- Call it straight from a click handler, with no `await` before it:
  Internet Identity's window opens only inside a click. Catch it as you catch
  `signIn()`.
- That is the window transport. With `transport: "redirect"`, `AuthClient`
  asks for `signIn()` and `requestAttributes()` to be called on the page's
  load, not from a click, each flow on a route of its own. So call it on each
  load of that route: `requestAttributes()` keeps the nonce across the loads,
  so the canister issues one.
- For a user who is signed in already, skip the sign-in: call
  `authClient.requestAttributes()` alone, with a new nonce, then the finish
  call.
- A failure after the sign-in leaves the user signed in without the
  attributes, so offer to try again.
- `_internet_identity_sign_in_finish` answers `variant { ok; err : … }`, so
  attributes the canister refuses reject as a `canister_err` whose `err.tag`
  says why (see [Errors](/v4/guides/errors/)). On `Stale` or `UnknownNonce`,
  ask for them again, with a new nonce. A signer the canister does not trust,
  or a canister with no `trusted_attribute_signers`, traps instead: a
  `rejected` error with reject code 5.
- The signer is the canister that minted the sign-in: Internet Identity's,
  `rdmx6-jaaaa-aaaaa-aaadq-cai`, on mainnet and in icp-cli's built-in one, or
  the `identityProvider` canister the factory is handed. The accounts canister
  must list it in `trusted_attribute_signers`.

### Which attributes to ask for

| Key              | What it is                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------- |
| `name`           | The name on the account the user signed in with                                                 |
| `email`          | An email address from that account. Internet Identity does not check it: treat it as user input |
| `verified_email` | Present only when Internet Identity established that the user controls the address              |

Grant access on `verified_email`, not `email`. `scopedKeys` from
`@icp-sdk/auth/client` scopes keys to the provider of a one-click sign-in, so
the user shares them in the same step:
`scopedKeys({ openIdProvider: "google", keys: ["verified_email"] })` is
`["openid:https://accounts.google.com:verified_email"]`. An organization's
SSO is the exception: `scopedKeys({ ssoDomain })` gives `sso:<domain>:name`
and `sso:<domain>:email`, with no `verified_email`, and the library takes the
email from `sso:<domain>:email` only for a domain the canister lists in
`trusted_sso_domains`.

<Aside type="caution" title="The canister checks, not the app">
  What the app holds is not proof. Any canister can sign attributes, so your
  canister must check that Internet Identity signed them, that their origin is
  your app's, and that their nonce is one it issued and has not used, within a
  few minutes. The `identity-attributes` library makes these checks; its README
  says how to configure them (`trusted_attribute_signers`, `frontend_origins`,
  `trusted_sso_domains`).
</Aside>

### Show what the user shared

`signInWithAttributes` returns what Internet Identity signed. Its `data` is a
Candid-encoded ICRC-3 `Value`: a `Map` of the requested keys, plus
`implicit:nonce`, `implicit:origin` and `implicit:issued_at_timestamp_ns`. A
scoped key stays scoped in the map. To show the user what they shared,
describe that type with candid-core's schema builders and read it with
`decode`:

```ts
import { c, type Schema } from "@candid-core/schema"
import { decode } from "@candid-core/schema/codec"

type Icrc3Value =
  | { tag: "Nat"; value: bigint }
  | { tag: "Int"; value: bigint }
  | { tag: "Blob"; value: Uint8Array }
  | { tag: "Text"; value: string }
  | { tag: "Array"; value: Icrc3Value[] }
  | { tag: "Map"; value: Array<[string, Icrc3Value]> }

const Icrc3Value: Schema<Icrc3Value> = c.rec(() =>
  c.variant({
    Nat: c.nat,
    Int: c.int,
    Blob: c.blob(),
    Text: c.text,
    Array: c.vec(Icrc3Value),
    Map: c.vec(c.tuple([c.text, Icrc3Value])),
  })
)

/** The text the attributes hold under `key`, for display. */
export function readAttribute(data: Uint8Array, key: string) {
  const decoded = decode(Icrc3Value, data) // never throws
  if (!decoded.ok) throw new Error(decoded.issues[0]?.message)
  const value = decoded.value as Icrc3Value // `decode` checked it against the schema

  if (value.tag !== "Map") return undefined
  const entry = value.value.find(([name]) => name === key)
  return entry?.[1].tag === "Text" ? entry[1].value : undefined
}
```

`readAttribute(attributes.data, "openid:https://accounts.google.com:name")`
is the name the user shared.
