# ic-reactor 4 in an app

This skill is a workflow. The API and its rules are in one guide that ships
with the package, `node_modules/@ic-reactor/core/llms.txt`: read it before
writing code, and follow it over anything here, including your memory of
earlier ic-reactor versions (their names are gone in 4).

This skill describes these versions:

- `@ic-reactor/core`: `4.0.0-alpha.0`
- `@ic-reactor/react`: `4.0.0-alpha.0`
- `@ic-reactor/vite-plugin`: `4.0.0-alpha.0`

## Workflow

1. **Read the installed guide.** Its `Applies to` line names the release it
   describes; when that differs from the list above, the installed guide wins.
2. **Install the exact peers.** `@ic-reactor/core` with `@icp-sdk/core` and
   `@tanstack/query-core`; for React, `@ic-reactor/react` (at exactly core's
   version), `@tanstack/react-query` and `react`; `@icp-sdk/auth` for Internet
   Identity sign-in. `@candid-core/schema` must be the exact version
   `@ic-reactor/core` lists in its `peerDependencies`, and the generator
   `@candid-core/cli` the exact version `@ic-reactor/vite-plugin` lists:
   install both with `--save-exact`.
3. **Generate the module** from each canister's `.did`, with
   `npx candid-core-cli gen <file>.did -o src/generated`, or with the Vite
   plugin, which regenerates on change:

   ```ts
   // vite.config.ts
   import { defineConfig } from "vite"
   import { icReactor } from "@ic-reactor/vite-plugin"

   export default defineConfig({
     plugins: [
       icReactor({
         canisters: {
           ledger: { didFile: "did/icrc1.did", outDir: "src/generated" },
         },
       }),
     ],
   })
   ```

   The module is named after the `.did` file: for `icrc1.did` both write
   `src/generated/icrc1.ts`, which the guide imports as `./generated/icrc1`.
   Without `outDir` the plugin writes to `src/canisters/`, and the imports
   must follow. Never edit the generated file; take method names and value
   shapes from its `type Actor`, and never guess them. In CI, `candid-core-cli gen ... --check`
   fails on a stale module.

4. **Create one client** with `createClient({ network, identity | auth })`:
   one per browser tab, or one per request on a server. Choose the network and
   the caller as the guide's Setup section says, including its rule for an
   identity that may be anonymous.
5. **In React**, render `ReactorProvider` with a client factory around the
   tree that calls canisters, and read the client and the caller with
   `useClient()` and `useAuth()`.
6. **Read and write** with `useQuery(client.queryOptions(...))` and
   `useMutation(client.mutationOptions(...))`, or call the canister's methods
   directly outside React. Build options in render from that render's
   `useClient()`, never from a module-scope client, and add neither `retry` to
   a write nor data carried across keys.
7. **Handle failures** by `isReactorError(error)`, then `kind` and
   `mayHaveExecuted`: when it is `true`, tell the user the outcome is unknown
   and re-read; never re-send.
8. **Test** through `createTestClient()` from `@ic-reactor/core/testing`, a
   real client over an in-memory replica, not with stubbed calls; then run the
   app's type check and tests.

## Before you finish

Check the code against the guide's "Do not" list, item by item.
